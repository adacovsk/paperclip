# Why the raw conflict path list overstates the work

**Justifies:** *Classify before you decide who owns the merge.* (§Landing sweep step 3)

`merge-tree`'s path list is a measurement of text, not of work. Two corrections separate them, and
both have parked branches on the operator that a Worker could have rebased in one run.

## `assets/schemas/**` is never independent work

Those files are generated by `cargo run --bin generate_schemas` from the Rust root types in
`src/bin/generate_schemas.rs`. A conflict in one is a *restatement* of the Rust conflict that
produced it. Hand-merging it is wrong twice over: it edits a build artifact, and the hand
resolution can silently disagree with what the generator emits. The correct resolution is to take
`origin/main`'s copy, rebase the Rust, and re-run the generator — which the Architect does at §6.5
before Landing anyway.

A task can be parked for operator merge on a count that is mostly regenerable files, which is why
the rule also requires **stating the excluded paths in the block comment**: the next reader needs
to see the count was filtered rather than mis-measured.

## One non-schema path is one author's intent

One file has one conflicting surface and one author's intent to recover — that is the Worker's own
change re-applied, and re-dispatching it costs one run. Reconciling *across* surfaces is the thing
an operator is needed for, so the threshold is two or more distinct non-schema paths. Misreading a
one-file conflict as a hand-merge left two tasks parked five days, and a third parked over a
one-word comment edit.

## A file and its own test are one surface

`foo.py` + `tests/test_foo.py`, or `src/x.rs` + `tests/x.rs`, conflict together because one change
touched both, and they rebase together too. A guard and its test change as one edit; counting them
as two paths is what pushes a one-surface conflict over the operator threshold.
